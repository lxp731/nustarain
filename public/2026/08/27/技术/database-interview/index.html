数据库面试问答：MySQL / PostgreSQL / Neo4j / Qdrant（34 题）

适用岗位：运维工程师 / 技术支持工程师 / AI 运维工程师 / DevOps 工程师

二、基础篇（12 题）

Q1. MySQL 的索引底层用的什么数据结构？为什么用 B+ 树不用哈希或 B 树？

  • 【考察点】是否真懂索引原理，还是只会背”索引能加速”；能不能说出 B+ 树的两个关键特性
  • 【参考回答】InnoDB 索引底层是 B+ 树：主键索引是聚簇索引，叶子节点存整行数据；二级索引叶子只存索引列加主键值。选 B+ 树有两个核心原因：一是非叶子节点只存键不存数据，一个 16KB 的页能放下上千个键，树更矮、IO 次数更少，三层就能支撑千万级数据；二是叶子节点之间有双向链表，范围查询和排序特别顺。哈希索引只能等值匹配、做不了范围查询，所以 InnoDB 里只有自适应哈希索引做辅助加速。相比 B 树，B+ 树把数据全放叶子且叶子有链表，范围扫描和顺序 IO 都更好。
  • 【追问】
    • 追问：为什么主键推荐自增整数、不推荐 UUID？→ 自增主键插入时只追加到 B+ 树最右叶子，几乎不触发页分裂；UUID 是随机的，插入要频繁分裂页、产生碎片，而且二级索引叶子存的是主键值，UUID 会让所有二级索引的存储翻倍。
    • 追问：三层 B+ 树大概能撑多少数据？→ 粗算：非叶子页一个键+指针约 10 字节，16KB 页能存约 1000 个键，叶子页一行约 1KB 能存约 16 行，1000×1000×16 约 1600 万行。
  • 【岗位标注】通用 / 运维

Q2. 一条 SELECT 语句在 MySQL 里是怎么执行的？

  • 【考察点】是否了解 MySQL 的 Server 层 + 存储引擎层架构，能不能按顺序说清各组件
  • 【参考回答】我一般按五步讲：第一步连接器，建立连接、校验账号密码和权限，所以改权限后要重连才生效；第二步分析器，做词法语法解析，语法错误在这层报；第三步优化器，决定用哪个索引、多表 join 的顺序，这是我们调优的主要对象；第四步执行器，调用存储引擎接口取数，权限校验也在这层做；第五步 InnoDB 存储引擎真正读写数据。8.0 之前还有查询缓存，因为命中率低、维护代价大，8.0 直接移除了。
  • 【追问】
    • 追问：优化器一定会选最优索引吗？→ 不一定，优化器按统计信息估算行数来选，统计信息过期（比如数据量暴涨）可能选错；常见做法是 ANALYZE TABLE 刷新统计，或者用 FORCE INDEX 强制指定。
    • 追问：UPDATE 的执行流程有什么不同？→ 流程类似，但 InnoDB 先查后改：定位行、加锁、写 undo log 记录旧值用于回滚，再更新，最后写 redo log 保证崩溃恢复。
  • 【岗位标注】通用 / 运维

Q3. EXPLAIN 怎么看？哪些字段最关键？

  • 【考察点】有没有真实排查过慢查询，还是只会说”explain 一下”
  • 【参考回答】我主要看四个字段：type 是访问类型，从好到坏大致是 system、const、eq_ref、ref、range、index、ALL，出现 ALL 就是全表扫描，是大问题；key 是实际用到的索引，key 为 NULL 说明没走索引；rows 是预估扫描行数，越大越危险；Extra 里出现 Using filesort（排序没走索引）、Using temporary（用了临时表）通常要优化。一条 SQL 如果 type 是 ALL、rows 上百万，基本就是问题 SQL，我会先看 type 和 rows，再决定是加索引还是改写法。
  • 【追问】
    • 追问：type=range 说明什么？→ 索引范围扫描，比如 BETWEEN、>、<、IN，属于可接受，但要关注 rows 别太大。
    • 追问：Extra 里 Using index 是什么意思？→ 覆盖索引，查询的列都在索引里不用回表，最理想的状态，可以刻意用联合索引去凑。
  • 【岗位标注】通用 / 运维 / 技术支持

Q4. 生产上怎么定位慢查询？

  • 【考察点】有没有在真实环境处理过性能问题，给的命令是否具体
  • 【参考回答】我分三步：第一步确保慢查询日志开着，SET GLOBAL slow_query_log=ON，long_query_time 设成 1（1 秒以上记录），生产更严格可以设 0.5；第二步用 mysqldumpslow -s at -t 10 慢日志路径 按平均耗时排序取前 10 条，或者用 pt-query-digest 做聚合分析；第三步对命中 SQL 跑 EXPLAIN 定位问题。实时出问题时直接 SHOW PROCESSLIST 看有没有长时间 Running 的语句，这个最快。
  • 【追问】
    • 追问：long_query_time 设太小有没有副作用？→ 记录本身开销小，主要风险是日志文件增长快，要做好轮转归档，或者直接接入监控系统。
    • 追问：如果慢查询日志里都是同一条 SQL 怎么办？→ 优先查缺索引，再看统计信息是否过期，最后看锁等待——慢不一定在查，可能在等锁。
  • 【岗位标注】运维 / 技术支持

Q5. 事务的 ACID 是什么？MySQL 是怎么实现的？

  • 【考察点】能不能把”背概念”升级为”讲机制”，特别是 undo log 和 redo log 的分工
  • 【参考回答】ACID 是原子性、一致性、隔离性、持久性。我的理解：原子性靠 undo log，事务失败或回滚时用 undo 里记录的旧值把数据改回去；一致性靠约束加事务机制共同保证；隔离性靠锁和 MVCC 多版本并发控制；持久性靠 redo log，而且是 WAL 机制——先写 redo log 再写数据文件，崩溃后重启用 redo 重放恢复没来得及落盘的数据，所以 InnoDB 崩了不会丢已提交事务。
  • 【追问】
    • 追问：innodb_flush_log_at_trx_commit 三个取值分别是什么？→ 1 每次提交都刷盘，最安全但最慢；0 每秒刷一次，最快但可能丢 1 秒数据；2 提交时写到 OS 缓存、每秒刷盘，OS 崩了会丢。生产一般用 1，追求性能可折中用 2。
    • 追问：redo log 写满了会怎样？→ redo log 是环形写，写满必须触发 checkpoint 把脏页刷盘，刷盘跟不上写入就会被卡住，表现为”写入突然变慢”。
  • 【岗位标注】通用 / 运维

Q6. MySQL 的隔离级别有哪些？默认是哪个？幻读怎么解决？

  • 【考察点】隔离级别很多人背得出来，能说清 MVCC + 间隙锁组合的才是真懂
  • 【参考回答】四个级别：读未提交（有脏读）、读已提交（解决脏读，但不可重复读）、可重复读（MySQL 默认，解决不可重复读）、串行化（全部串行加锁）。MySQL 在可重复读下解决幻读是组合拳：普通查询走 MVCC 快照读，靠快照天然看不到别的事务新插入的行；当前读（SELECT … FOR UPDATE / UPDATE / DELETE）走行锁加间隙锁，也就是 next-key lock，把范围内和边界上的间隙都锁住，别的事务插不进新行，幻读就没了。
  • 【追问】
    • 追问：为什么 MySQL 默认可重复读，而 Oracle 默认读已提交？→ 历史原因：MySQL 早期 binlog 用 statement 格式，读已提交下回放 binlog 可能产生数据不一致，可重复读配合 next-key lock 能保证 binlog 回放结果一致；后来 row 格式解决了这个问题，但默认值保留至今。
    • 追问：把隔离级别改成读已提交有什么好处？→ 间隙锁基本消失，死锁和锁冲突明显减少，很多高并发业务会主动降级到 RC。
  • 【岗位标注】通用 / 运维 / 技术支持

Q7. MySQL 有哪些锁？间隙锁和死锁是怎么回事？

  • 【考察点】锁是生产事故高发区，想确认你能不能讲清锁的粒度和死锁成因
  • 【参考回答】按粒度分表锁和行锁。InnoDB 的行锁有三种：记录锁（锁具体一行）、间隙锁（锁两个索引值之间的区间，防止插入）、next-key lock（记录锁+前向间隙锁，InnoDB 默认的区间锁形态）。死锁就是两个事务互相持有对方需要的锁，比如 A 锁了行 1 等行 2，B 锁了行 2 等行 1。MySQL 会自动检测死锁并回滚代价小的一方，报 ERROR 1213。我处理死锁的思路是：用 SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK 部分，两个事务在哪些语句等哪些锁一目了然。
  • 【追问】
    • 追问：怎么预防死锁？→ 三个常用手段：多行操作按固定顺序加锁（如按主键排序后更新）、事务尽量短（少做无关查询）、让锁粒度更小（走主键/唯一索引，避免锁一大片范围）。
    • 追问：什么情况下行锁会变成锁一大片？→ 更新条件没走索引时，InnoDB 会锁住所有扫描到的行，等于全表锁，这是”慢 SQL 拖垮全库”的常见原因。
  • 【岗位标注】通用 / 运维 / 技术支持

Q8. MySQL 主从复制的原理是什么？binlog 是什么？

  • 【考察点】主从是运维岗必考核心，需要能画出完整链路并说出 binlog 格式
  • 【参考回答】主从复制是异步的，链路是：主库把变更写进 binlog → 从库的 IO 线程连上主库拉取 binlog 写入本地 relay log（中继日志）→ 从库的 SQL 线程把 relay log 重放执行。binlog 是 Server 层的逻辑日志，记录”做了什么”，三种格式：statement（记 SQL）、row（记行变更，5.7.7 起默认，最安全）、mixed（混合）。它是主从复制、增量备份、误删恢复的基础。
  • 【追问】
    • 追问：主从之间会不会丢数据？→ 标准异步复制会丢：主库提交后、从库还没拉走就宕机，这部分数据就没了；所以有半同步复制（semi-sync），主库要等至少一个从库确认收到 binlog 才提交，RPO 接近 0，但会拖慢主库写入。
    • 追问：为什么从库要配只读（read_only）？→ 防止程序误写从库导致主从不一致；read_only 不影响主库复制线程写入。
  • 【岗位标注】运维 / DevOps

Q9. 数据库怎么备份和恢复？mysqldump 和 xtrabackup 怎么选？

  • 【考察点】备份恢复是运维底线技能，面试官会看你有没有实操细节和恢复演练意识
  • 【参考回答】两条路线：逻辑备份用 mysqldump，物理备份用 xtrabackup。mysqldump 适合中小库，关键参数是 --single-transaction（InnoDB 下做一致性快照不锁表）和 --master-data=2（记录备份时刻的 binlog 位置，方便做增量）；缺点是慢，恢复是逐条执行 SQL。xtrabackup 适合大库，命令是 xtrabackup --backup --target-dir=... 备份、--prepare 应用 redo log 使备份一致、--copy-back 恢复，直接拷数据文件加 redo log，速度快、几乎不停机。原则：大库用 xtrabackup、小库用 mysqldump，不管哪种，binlog 都要保留才能做时间点恢复。最重要的是定期做恢复演练——没验证过的备份等于没有。
  • 【追问】
    • 追问：误删了一张表怎么恢复？→ 有全备就恢复全备+binlog 增量追到误删前的位置；没全备但 binlog 是 row 格式且还留着，可以用 mysqlbinlog 按 position 或时间点重放，把误删前的操作补回来。
    • 追问：mysqldump 为什么不锁表？→ 加 –single-transaction 后用 InnoDB 的 MVCC 快照做一致读，备份期间数据文件被改也没关系；但如果混着 MyISAM 表，MyISAM 还是要锁表。
  • 【岗位标注】运维 / DevOps

Q10. 数据库出现乱码怎么排查和处理？

  • 【考察点】技术支持岗高频真实问题，考排查顺序，以及”乱码可能已经写坏”这个坑
  • 【参考回答】我的排查顺序：先 SHOW VARIABLES LIKE 'character_set%' 看 server、database、connection 的字符集是否统一；再看建表语句的 charset 和字段的 collation。乱码的本质是写入编码和读取编码不一致——如果是”客户端用 latin1/GBK 写入、库里是 utf8”，数据可能已经被转错编码存进去了，这种光改连接参数救不回来，得用 CONVERT 或重新导入。正确姿势：库表统一 utf8mb4（能存 emoji 和生僻字），连接串显式指定编码，客户端 SET NAMES utf8mb4。
  • 【追问】
    • 追问：utf8 和 utf8mb4 有什么区别？→ utf8 是 MySQL 的别名，最多 3 字节，存不了 emoji（4 字节）；utf8mb4 才是真正的 4 字节 UTF-8，MySQL 8.0 默认就是 utf8mb4。
    • 追问：已经乱码的数据怎么救？→ 判断是否可逆：如果只是显示层问题，改客户端连接编码即可；如果是入库时被双重转码写坏，要么用 CONVERT 反向转换尝试恢复，要么接受从源头重新导入，并立刻统一全链路字符集。
  • 【岗位标注】技术支持 / 运维

Q11. 连接池是干什么的？连接数打满怎么办？

  • 【考察点】高并发场景常识，考”连接是稀缺资源”的意识，以及具体排查命令
  • 【参考回答】建一个数据库连接要 TCP 握手加认证，开销很大，所以用连接池复用，程序侧是 HikariCP/Druid，运维侧还可以用 ProxySQL 做连接池和读写分离。生产上连接数打满（报 Too many connections）我按这个顺序查：先 SHOW PROCESSLIST 看连接都在干嘛，八成是慢 SQL 或长事务把连接占住不释放；再看 SHOW STATUS LIKE 'Threads_connected' 和 max_connections 的比值；最后看应用侧连接池是不是配大了。处理：临时 SET GLOBAL max_connections 调大应急，根治是杀慢 SQL、调连接池和超时参数。
  • 【追问】
    • 追问：max_connections 默认多少？调太大有什么风险？→ 默认 151；调太大没意义，几千个连接同时干活上下文切换开销爆炸，更合理的是控制连接数、让每条 SQL 都快。
    • 追问：wait_timeout 是干嘛的？→ 控制空闲连接多久被断开，默认 8 小时；设太短连接容易被断导致程序报错，太长会占着连接池名额。
  • 【岗位标注】运维 / 技术支持 / DevOps

Q12. PostgreSQL 和 MySQL 的主要区别？

  • 【考察点】简历里两个都写了，面试官大概率对比着问，考是否真实用过 PG
  • 【参考回答】我理解的核心区别有三层：第一，MVCC 实现不同——MySQL 靠 undo log 存旧版本，PG 是多版本堆，旧版本行直接留在数据页里靠可见性判断，所以 PG 没有回滚段概念，但会带来表膨胀（dead tuple），要靠 autovacuum 清理；第二，功能上 PG 更”重”——原生支持 JSONB（有 GIN 索引，能在 JSON 内部走索引查询）、数组、全文检索、物化视图，SQL 标准遵守度更高；第三，日志——PG 的 WAL 是物理日志，wal_level、max_wal_size、pg_wal 目录这些运维时都要关注。MySQL 的优势是生态大、主从简单、运维资料多，读多写少的互联网场景很成熟。
  • 【追问】
    • 追问：JSONB 和 MySQL 的 JSON 有什么区别？→ PG 的 JSONB 是二进制存储，支持 GIN 索引，WHERE data->>'name'='x' 可以走索引；MySQL 的 JSON 8.0 才有，功能相对简单，能用关系表还是用关系表。
    • 追问：PG 的 autovacuum 是什么？→ 自动清理 dead tuple 并更新统计信息的后台进程，配置不当（比如关掉）会导致表膨胀、查询变慢，是 PG 运维最常见的坑之一。
  • 【岗位标注】通用 / 运维 / AI 运维

三、进阶篇（12 题）

Q1. 联合索引的最左前缀原则是什么？怎么设计联合索引？

  • 【考察点】索引设计是 MySQL 核心实践题，考能不能结合业务场景设计索引
  • 【参考回答】联合索引 (a,b,c) 本质是先按 a 排、a 相同再按 b 排、再按 c 排，所以查询必须从最左的 a 开始连续使用索引列才能命中：能走 (a)、(a,b)、(a,b,c)，单独查 b 或 c 走不了。设计口诀是”等值在前、范围在后、区分度高的放前面”：比如 WHERE a=? AND b>10，索引应建 (a,b) 而不是 (b,a)；范围条件后面的列索引就失效了。还要想能不能做成覆盖索引，把高频查询的列都塞进索引避免回表。
  • 【追问】
    • 追问：WHERE a=? AND c=? 能用到 (a,b,c) 索引吗？→ 能用到 a 这一个列定位，但 c 用不上，中间隔着 b；除非单独建 (a,c)，或利用 8.0 的索引跳跃扫描（Skip Scan）。
    • 追问：索引建得越多越好吗？→ 不是，每个索引都有写放大和存储成本，更新表时要同步维护；一般单表控制在 5 个以内，用慢查询日志驱动加索引，而不是拍脑袋。
  • 【岗位标注】通用 / 运维 / 技术支持

Q2. 什么是回表？什么是覆盖索引？

  • 【考察点】考对 InnoDB 聚簇索引结构的理解，以及用索引优化查询的实战意识
  • 【参考回答】InnoDB 里主键索引的叶子存整行数据，叫聚簇索引；二级索引的叶子只存索引列加主键值。如果查询的列二级索引里没有，就要拿主键回主键索引查一次整行，这就是回表。覆盖索引就是查询所需的所有列都包含在某个索引里，比如建了 (name, age)，查 SELECT name, age FROM t WHERE name=’x’，直接从二级索引叶子拿数据，Extra 显示 Using index，不用回表，省一次随机 IO。
  • 【追问】
    • 追问：为什么回表慢？→ 回表是按主键做一次随机 IO，数据量大时几百万次回表就是几百万次磁盘随机读，比顺序扫索引慢一个数量级。
    • 追问：怎么判断有没有回表？→ 看 EXPLAIN 的 Extra 字段，有 Using index 就是覆盖，没有就可能回表。
  • 【岗位标注】通用 / 运维

Q3. MVCC 的原理是什么？快照读和当前读有什么区别？

  • 【考察点】事务隔离的核心机制，想确认你不是只会背隔离级别名字
  • 【参考回答】MVCC 就是多版本并发控制：每行数据有隐藏的 trx_id 记录最后修改它的事务，还有 roll_pointer 指向 undo log 里的旧版本链。事务开始时会生成一个 ReadView（活跃事务列表），快照读根据 ReadView 判断行版本是否可见，读到一个一致的历史快照，读不加锁，所以并发读不阻塞。可重复读和读已提交的区别就在于 ReadView 是事务开始就固定、还是每条语句都新建。当前读（SELECT … FOR UPDATE、UPDATE、DELETE）必须读最新版本，所以要加锁。
  • 【追问】
    • 追问：为什么可重复读下快照读看不到别的事务新插入的行？→ 因为 ReadView 固定了，新插入行的 trx_id 大于 ReadView 的最大活跃事务，判定不可见，这就是快照读层面幻读的解法。
    • 追问：长事务会有什么问题？→ undo log 版本链会很长、占空间、清理不掉，MySQL 里还可能导致历史版本太多，purge 线程来不及清，表空间膨胀。
  • 【岗位标注】通用 / 运维

Q4. 线上死锁怎么定位和处理？给个具体例子。

  • 【考察点】能不能给出完整的排查闭环：定位、看懂、解决
  • 【参考回答】定位就一条命令：SHOW ENGINE INNODB STATUS，看 LATEST DETECTED DEADLOCK 段，里面有两条 SQL 和各自持有的锁、等待的锁。我举个真实例子：事务 A 执行 UPDATE t SET x=1 WHERE id>10 AND id<20，锁住该区间的 next-key lock；事务 B 先 INSERT INTO t VALUES (15,...) 等间隙锁，同时事务 A 也想 INSERT 15，于是 A 等 B 的插入意向锁、B 等 A 的间隙锁，死锁。处理：报 ERROR 1213 回滚一边，业务重试即可恢复；根治是把隔离级别降到读已提交（间隙锁基本消失），或让事务按固定顺序、缩短事务范围。
  • 【追问】
    • 追问：死锁和锁等待超时是一回事吗？→ 不是，死锁是循环等待，MySQL 主动检测并回滚；锁等待超时是单方面等一把锁超过 innodb_lock_wait_timeout（默认 50 秒）直接报错。
    • 追问：死锁频繁怎么办？→ 优先查是不是索引没走对导致锁范围过大，其次看是不是多个事务都做大范围区间更新，改成按主键小批量处理。
  • 【岗位标注】运维 / 技术支持

Q5. 主从延迟一般什么原因？怎么处理？

  • 【考察点】主从延迟是运维高频事故，考对复制架构的深度理解，包括 5.7 之后的并行复制
  • 【参考回答】延迟的本质是从库回放赶不上主库写入。常见原因和对应处理：第一，大事务，一条 UPDATE 影响几十万行，回放很久，处理是拆小事务；第二，从库单线程回放（老版本），主库并发一高就跟不上，5.7 之后开多线程复制 MTS（slave_parallel_workers=4~8）按库或按事务并行；第三，从库上有慢查询或锁冲突抢资源；第四，网络带宽。监控用 SHOW SLAVE STATUS（8.0 是 SHOW REPLICA STATUS）的 Seconds_Behind_Master，但这个值不准——主库写入停了它也会归零，真正准的是比较主从的 binlog 位置差或 GTID 差。
  • 【追问】
    • 追问：GTID 是什么？有什么用？→ 全局事务标识符，主从切换、追增量、复制排错时不用手动对 binlog 文件名和位置，靠 GTID 自动定位，8.0 默认开启。
  • 【岗位标注】运维 / DevOps / AI 运维

Q6. PostgreSQL 的 WAL 是什么？JSONB 怎么用索引？

  • 【考察点】PG 运维的核心机制，考 WAL 和 JSONB 这两个最能代表”会用 PG”的点
  • 【参考回答】WAL 是写前日志，PG 所有数据修改先写 WAL 再落数据页，崩溃后靠 WAL 重放恢复，是 PG 不丢数据的基础。运维相关参数：wal_level（默认 replica，流复制要求不能低于它）、max_wal_size（默认 1GB，控制 checkpoint 触发频率）、pg_wal 目录大小要监控，WAL 增长异常一般是长事务或大写入。JSONB 建 GIN 索引：CREATE INDEX idx ON t USING GIN (data)，然后 WHERE data @> '{"name":"x"}' 这种包含查询就能走索引；单键等值可以用 data->>'name' 配合表达式索引。
  • 【追问】
    • 追问：checkpoint 是什么？→ 把 WAL 里已确认的变更刷到数据文件的动作；checkpoint 太频繁说明 max_wal_size 太小会拖慢写入，太少则崩溃恢复时间变长。
    • 追问：pgvector 是什么？→ PG 的向量扩展，加 vector 类型，支持 L2/内积/余弦距离，还有 IVFFlat 和 HNSW 索引，等于把向量检索塞进 PG，小规模 RAG 场景很实用，也是我们项目里对比过的方案。
  • 【岗位标注】运维 / AI 运维

Q7. Neo4j 适合什么场景？和关系型数据库比有什么本质区别？Cypher 怎么写？

  • 【考察点】考简历里”图数据库协同架构”是不是真落地过，以及能不能说清图的本质优势
  • 【参考回答】Neo4j 适合关系密集型场景：社交网络好友关系、知识图谱、权限体系、风控反欺诈关系链、推荐系统。它和关系型数据库的本质区别：关系是一等公民，存储上是邻接表结构，节点直接持有指向邻居的指针，遍历多跳关系是局部访问；而关系型数据库查”3 跳以内的朋友”要做三次 self-join，几百万节点的图基本跑不动。Cypher 是声明式语言，比如查”张三 3 跳内认识的李四”：MATCH (a:Person {name:'张三'})-[:KNOWS*1..3]-(b:Person {name:'李四'}) RETURN a,b；建关系：MATCH (a:Person),(b:Person) WHERE ... CREATE (a)-[:KNOWS {since:2020}]->(b)；索引用 CREATE INDEX FOR (p:Person) ON (p.name)。
  • 【追问】
    • 追问：什么情况下图数据库反而不合适？→ 纯事务型、强一致、报表聚合类场景不合适，比如订单、账务还是要关系型；图库适合”关系查询深度大、单点写入不高”的场景。
    • 追问：Larklex 项目里 Neo4j 存什么？→ 实体与实体之间的关系图谱，比如文档、标签、知识条目之间的关联，配合 Qdrant 做”向量召回+图谱路径校验/扩展”的知识增强，让 RAG 回答更准。
  • 【岗位标注】AI 运维 / 通用

Q8. 向量数据库的原理是什么？embedding 是什么？

  • 【考察点】AI 运维岗必考基础，考你能不能把”向量”讲得让不懂的人也能懂
  • 【参考回答】embedding 就是把文本、图片、音视频这类非结构化数据，用模型（比如 BGE、text-embedding-3）映射成高维向量（常见 768 或 1024 维），语义相近的内容向量距离就近，比如”苹果”和”水果”的向量比”苹果”和”汽车”近。向量数据库干的事就是存这些向量，并提供”给定查询向量，找出最相似的 K 个向量”的能力，底层是 ANN（近似最近邻）算法，因为高维空间做精确最近邻计算量太大。所以向量检索本质是语义搜索：不靠关键词匹配，靠语义相似度。
  • 【追问】
    • 追问：向量维度是不是越大越好？→ 不是，维度越高表达越丰富，但存储和计算开销线性增长、检索变慢，768~1536 维是常用区间，够用就好。
    • 追问：向量检索的”召回”和”精排”是什么？→ 召回阶段用向量粗筛出 Top-K，精排阶段再用更重的模型（如 reranker）重排，RAG 链路里两者配合。
  • 【岗位标注】AI 运维 / 通用

Q9. 余弦相似度、点积、L2 距离分别怎么选？

  • 【考察点】向量检索选型的核心细节，考是否真配过 Qdrant 的 distance 参数
  • 【参考回答】Qdrant 创建 collection 时要指定 distance：Cosine、Dot、Euclid 三选一。我的选择逻辑：文本语义检索默认 Cosine（只关心方向、不关心长度，对长短文本差异不敏感）；如果 embedding 已归一化（模长为 1），Cosine 和 Dot 数学上等价，但 Dot 计算更快（少一次归一化），所以归一化场景选 Dot；Euclid（L2）适合图像类 embedding，因为图像模型训练时通常按欧氏距离优化。有个坑：distance 是建 collection 时定死的，后面不能改，只能重建 collection 重新导入，所以选型要想清楚。
  • 【追问】
    • 追问：Qdrant 里 score 和距离是什么关系？→ Qdrant 返回的是 score，Cosine/Dot 越大越相似，Euclid 越小越相似；文档统一叫 score 是为了语义一致，Euclid 时底层是距离转换。
    • 追问：换 embedding 模型要不要重建向量？→ 要，不同模型的向量空间不可比，换模型旧向量全部失效，必须用新模型全量重算，这通常是重建 collection 的时机。
  • 【岗位标注】AI 运维

Q10. HNSW 索引的原理是什么？参数怎么调？

  • 【考察点】向量索引的深度题，考你对 HNSW 的理解不是停留在”知道名字”
  • 【参考回答】HNSW 是分层可导航小世界图：按层级组织，上层是稀疏的长程连接（用来快速跳到目标区域），下层是密集的短程连接（精细查找），搜索时从顶层逐层往下，每层做贪婪最近邻游走，不需要全量扫描，所以查询是亚线性复杂度。Qdrant 里关键参数：M 是每个节点的最大连接数（默认 16，越大越准但内存越多）、ef_construct 是建图候选数（默认 100，越大图质量越高建库越慢）、ef 是查询候选数（请求级参数，越大越准越慢）。调优思路：先跑 baseline，再逐步提高 ef 观察召回率和延迟的 trade-off，别一上来就拉到最大。
  • 【追问】
    • 追问：HNSW 和暴力检索差距多大？→ 百万级向量下暴力检索要算一百万个点积，从毫秒级变秒级；HNSW 通常几毫秒到几十毫秒，代价是少量召回损失（一般 95%+ 没问题）。
    • 追问：HNSW 内存占用为什么高？→ 每个节点的邻居列表要常驻内存，M 越大图越密内存越多；超大数据集要考虑内存成本，Qdrant 支持 mmap 让部分数据落盘。
  • 【岗位标注】AI 运维 / 运维

Q11. Qdrant 的 collection 和 segment 是什么关系？过滤条件怎么用？

  • 【考察点】考 Qdrant 的实际运维细节，没真用过的人答不出 segment 和 payload 索引
  • 【参考回答】collection 是逻辑上的数据集，创建时定向量维度、distance 和 HNSW 参数；一个 collection 内部会被拆成多个 segment 存储，每个 segment 是独立存储单元（有自己的 HNSW 图），新数据先进内存段，达到阈值（默认 20000 点）后优化器自动合并/固化到磁盘段，要监控 segment 数量——段太多会拖慢检索。过滤是 Qdrant 的杀手锏：点可以带 payload（元数据），检索时用 filter 先圈定范围，POST /collections/{name}/points/search 带 "filter":{"must":[{"key":"tenant_id","match":{"value":"a"}}]}，配合 payload 索引（KEYWORD/INTEGER 等类型）才能快，否则过滤会全段扫描。
  • 【追问】
    • 追问：多租户场景怎么设计？→ 经典做法是每个租户的 payload 带 tenant_id 并建 KEYWORD 索引，检索时强制 filter；隔离要求高、量大的也可以一租户一 collection。
    • 追问：怎么检查 collection 的健康状态？→ GET /collections/{name} 看 status（green/yellow）、points_count、indexed_points、segments_count；indexed_points 远小于 points_count 说明向量还没全建索引，检索会偏慢。
  • 【岗位标注】AI 运维

Q12. pgvector、FAISS、Qdrant 怎么选？Larklex 为什么这么搭？

  • 【考察点】几乎必考，因为简历原文写了”协同架构设计”，面试官就是要听选型论证
  • 【参考回答】三者定位不同：pgvector 是 PG 扩展，优势是零额外组件、和业务 SQL 在一起、事务里能联合查询，适合百万级以下、原型验证、运维简单的场景；FAISS 是库不是服务，性能最好最灵活，但持久化、并发、过滤、高可用全要自己写，不适合团队直接上生产；Qdrant 是独立向量数据库服务，开箱即用有 REST/gRPC、payload 过滤、HNSW 成熟、快照备份、支持集群分片，运维成本可控。Larklex 的搭法：PG 存业务主数据和元数据（结构化、强一致）、Neo4j 存实体关系图谱、Qdrant 存跨模态 embedding 向量——检索时先 Qdrant 向量召回，再 Neo4j 关系信息校验/扩展，最后 PG 回填业务详情，各司其职。
  • 【追问】
    • 追问：为什么不用 pgvector 一个搞定？→ 项目里向量量级和过滤复杂度超出 pgvector 的舒适区，Qdrant 的 payload 过滤、快照、独立扩缩容更适合生产；pgvector 我们做了对比验证，结论是”原型可以，生产选 Qdrant”。
    • 追问：这三个库的数据怎么保持一致？→ 向量和元数据天然是最终一致：业务写 PG 成功后异步写 Qdrant（消息队列兜底重试），定期全量对账，删除时两边都要清；Neo4j 图谱更新同理，事件驱动。
  • 【岗位标注】AI 运维 / 通用

四、生产实战·刁钻篇（10 题）

Q1. 线上一条 SQL 原来 10ms，现在突然 10 秒，怎么排查？

  • 【考察点】综合排查能力，考排查顺序和分诊思路，没实操过的人给不出完整链路
  • 【参考回答】我不会一上来就加索引，按这个顺序分诊：第一步看慢查询日志和监控，确认是这条 SQL 变慢还是整库变慢（整库变慢多半是资源或锁，单条变慢多半是执行计划问题）；第二步 SHOW PROCESSLIST 看它是不是在等锁（State 是 Waiting for lock 还是 executing）；第三步 EXPLAIN 看 type/rows 是否变化，检查索引是否失效、统计信息是否过期（ANALYZE TABLE 刷新）；第四步看数据量是不是涨了数量级，或索引被 DDL 重建过；最后看 IO/CPU 有没有被打满。最常踩的坑：表加了新字段导致查询从覆盖索引变成回表，或者隐式类型转换让索引失效。
  • 【追问】
    • 追问：怎么判断是”查得慢”还是”等锁等得慢”？→ 看 PROCESSLIST 的 State：executing 是真正在查，Waiting for lock 是等锁；等锁的锅在别的事务身上，查 Information_schema.INNODB_TRX 找持锁事务。
    • 追问：统计信息没问题、索引也在，还是慢呢？→ 看返回行数和回表量，可能数据在磁盘、缓存命中率低（Buffer Pool 命中率低于 95%），这时扩大 innodb_buffer_pool_size 比加索引有效。
  • 【岗位标注】运维 / 技术支持 / DevOps

Q2. 主从延迟导致业务读到旧数据，怎么办？

  • 【考察点】考读写分离架构下的”一致性兜底”设计，是架构思维题
  • 【参考回答】先明确业务容忍度，再分层处理：第一，强一致的读（比如”我刚下的单立刻要看到”）强制走主库，写后 1 秒内的读都路由主库；第二，可容忍的读接受延迟并设置告警（Seconds_Behind_Master 超 30s 报警），延迟超阈值时把流量切回主库兜底；第三，根因治理——拆大事务、开并行复制、从库加索引让回放变快、避免从库跑重报表任务。架构上更彻底的是半同步复制，或用中间件做”读己之写”路由。
  • 【追问】
    • 追问：为什么从库回放会比主库执行慢？→ 主库是并发执行，从库串行重放（或并行度低），一条大事务在从库是单线程跑完；另外从库通常还扛着读流量，资源互相挤占。
    • 追问：有没有监控延迟更准的方法？→ 比较主从的 GTID 或 binlog 位置差（主库 SHOW MASTER STATUS 的 File/Position 与从库 SHOW SLAVE STATUS 对比），比 Seconds_Behind_Master 可靠。
  • 【岗位标注】运维 / DevOps

Q3. 半夜主库挂了，怎么切换？要注意什么？

  • 【考察点】应急预案题，考流程完整性和”丢数据”意识，最喜欢追问细节
  • 【参考回答】我的切换流程：第一步确认主库确实不可用（网络、进程、磁盘都看一遍，别误判）；第二步看有没有现成的 MHA/Orchestrator 自动切换，没有就手动：选一个 relay log 追得最接近主库的从库，SHOW SLAVE STATUS 确认后 STOP SLAVE、RESET SLAVE ALL，SET GLOBAL read_only=OFF 提升为主；第三步改应用连接（DNS/配置中心/代理层切流量），从库们重新 CHANGE MASTER TO 指向新主；第四步原主库恢复后不要直接加回集群，先作为从库追数据，追平再转正。最重要的提醒：异步复制下主库宕机必然可能丢最后一点数据，切换前评估 RPO 能不能接受，接受不了就要上半同步；而且切换一定要有预案演练，没演练过的手动切换最容易出事故。
  • 【追问】
    • 追问：怎么选”最接近主库”的从库？→ 看 relay log 回放进度，选 IO 线程拉到最新、SQL 线程追得最紧的；GTID 环境下看 gtid_executed 集合的差异。
    • 追问：切换后原来的主库怎么办？→ 清掉旧 binlog 身份，作为新主的从库重新建复制，先追平再让读流量慢慢回来，别立刻加回。
  • 【岗位标注】运维 / DevOps

Q4. 有人手滑 DELETE 删了整张表的线上数据，怎么恢复？

  • 【考察点】备份恢复的真实演练题，考有没有完整恢复 SOP 和”时间点恢复”的实操
  • 【参考回答】先说结论：能不能恢复取决于有没有备份和 binlog。标准流程：第一步立刻冻结写入（避免新数据污染），确认删除时间点；第二步找最近的 xtrabackup 全备或 mysqldump 全备，恢复到临时实例（先 –prepare 使备份一致）；第三步用 binlog 增量追到误删前一刻：mysqlbinlog --start-position=全备binlog位置 --stop-datetime='2024-xx-xx xx:xx:xx' binlog.000xxx | mysql -h 临时实例；第四步把恢复出的表导出导回生产，或直接切换临时实例。前提是 binlog_format=row 且 binlog 还留着，否则只能恢复到全备时刻，会丢中间数据。所以我的原则：备份天天有，恢复演练季季做，binlog 保留周期对齐 RPO 要求。
  • 【追问】
    • 追问：为什么用 binlog 而不是直接看数据？→ DELETE 不留”回收站”，row 格式 binlog 记录每行删除前的完整值，mysqlbinlog -vv 能看到，理论上能反向拼出被删数据，这也是 row 格式比 statement 安全的原因。
    • 追问：如果没有 binlog 呢？→ 只能恢复到全备时刻，损失全备之后到删除之间的所有变更；所以关键业务表可以配延迟从库（故意延迟回放 1~2 小时），出事直接从这个延迟从库捞数据，是很实用的兜底手段。
  • 【岗位标注】运维 / DevOps

Q5. 线上频繁报死锁，你怎么定位到具体原因？

  • 【考察点】把死锁从”知道概念”拉到”能处理线上事故”的题，考具体命令和案例复现能力
  • 【参考回答】第一步 SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK，里面有两条 SQL、持锁和等待锁的详细信息，这是最直接的现场；第二步 SHOW PROCESSLIST 看还在跑的连接，找出同类事务的高频入口；第三步看这两条 SQL 的执行计划，核心是检查锁的范围——如果 UPDATE/INSERT 的条件没走索引，锁的就是大范围甚至全表，两个事务必然互相踩。我遇到过一个典型：两个任务都先 SELECT ... FOR UPDATE 查同一张表的区间，再反向更新另一张表，顺序不一致导致循环等待。解决：统一加锁顺序+让条件走索引缩小锁范围+事务里去掉不必要的大区间扫描。
  • 【追问】
    • 追问：死锁检测本身会不会影响性能？→ MySQL 每次加锁失败都会检查等待图，并发高时有开销，但通常远小于死锁本身的代价；可以调 innodb_deadlock_detect 关闭检测靠锁超时兜底，但一般不建议关。
    • 追问：为什么说”回滚代价小的事务”？→ InnoDB 按每个事务修改的行数估算回滚代价，回滚行数少的那个，把锁让出来让另一个继续。
  • 【岗位标注】运维 / 技术支持

Q6. Qdrant 检索突然变慢，怎么排查和优化？

  • 【考察点】向量库运维的实战题，考对 segment、索引状态、内存这些细节的掌握
  • 【参考回答】按这个顺序查：第一步 GET /collections/{name} 看 status 和 indexed_points vs points_count——如果向量导入后还没建完索引，检索会退化到暴力扫描，这是最常见的”突然变慢”原因；第二步看 segments_count，段太多（比如几十个）说明优化器没及时合并，检索要跨段查，可以调 optimizer 的合并目标或手动合并；第三步看 filter 的 payload 字段有没有建索引，没索引的过滤会全段扫描 payload；第四步看 HNSW 参数，ef、ef_construct、M 调太大都会拖慢；最后看机器资源——内存不足时 segment 落到磁盘（mmap），IO 打满就慢。优化动作：等/触发索引完成、合并段、给过滤字段建 payload 索引、必要时加副本分担查询。
  • 【追问】
    • 追问：怎么触发向量索引？→ Qdrant 默认向量数超过 20000 会自动开始建索引（indexing_threshold），可以调小阈值或手动触发；索引过程本身吃 CPU，要避开业务高峰。
    • 追问：查询量上来了怎么扩容？→ Qdrant 集群模式按 collection 分片（shard），可以加副本（replication factor）做读写分离——写入走主分片、查询均摊到副本；注意分片数创建后不能改，一开始就要按预估规模规划。
  • 【岗位标注】AI 运维

Q7. PG 和 Qdrant 双写，怎么保证两边数据一致？

  • 【考察点】RAG 架构的工程细节题，考对分布式系统”最终一致性”的落地能力，这是简历亮点的高频追问
  • 【参考回答】我明确先说结论：这种跨库架构做不到强一致，目标就是”最终一致+对账兜底”。落地分三层：第一层写入顺序，业务事务只写 PG（源数据），成功后发消息到消息队列（Kafka/RabbitMQ），消费者异步写 Qdrant，写失败自动重试，重试还失败进死信队列人工处理；第二层补偿，删除/更新同样走异步，保证两边同生共死；第三层对账，定期（比如每小时）按主键清单比对 PG 和 Qdrant，发现缺失或过期向量就重算补写。注意：embedding 计算是重操作，别放在业务请求链路里同步做，应该异步化。这样 PG 的强一致性和事务能力不受影响，向量库的延迟写入被队列削峰。
  • 【追问】
    • 追问：业务已写 PG 但向量没写成功，检索会怎样？→ 新数据短时间搜不到，属于可接受的最终一致窗口；对实时性要求高的可以读时兜底（检索没命中再查 PG 补算），一般没必要。
    • 追问：为什么不用 CDC（如 Debezium）？→ CDC 更优雅，监听 binlog/WAL 自动同步，不需要业务改代码；但引入组件和运维复杂度，数据量小时消息队列方案更简单可控，量大了再迁 CDC。
  • 【岗位标注】AI 运维 / DevOps

Q8. 哪些写法会导致索引失效？给几个生产常见例子。

  • 【参考回答】常见六种：第一，对索引列用函数或运算，WHERE YEAR(create_time)=2024 不走索引，改成 create_time BETWEEN '2024-01-01' AND '2024-12-31' 就能走；第二，隐式类型转换，字符串列和数字比 WHERE phone=138xxxx（phone 是 varchar），MySQL 会把列转成数字导致索引失效，统一类型或加引号；第三，前导模糊 WHERE name LIKE '%张' 走不了，’张%’ 可以；第四，OR 连接的条件有一个没索引，整个查询可能全表扫，改成 UNION ALL 或都建索引；第五，联合索引不满足最左前缀；第六，排序和索引顺序不一致导致 filesort。排查就盯 EXPLAIN 的 type 是不是从 ref/range 掉到了 ALL。
  • 【追问】
    • 追问：为什么对列做函数就失效？→ 索引里存的是原始值，函数运算后没法直接二分定位，等于要对每一行的值都算一遍函数，MySQL 只能放弃索引（8.0 支持函数索引/表达式索引可以绕开）。
    • 追问：LIKE ‘%张%’ 真的完全没救吗？→ 右侧通配符 ‘张%’ 可以走索引；两侧都有只能全扫，或考虑全文索引、前缀索引，或者用 ES/向量检索这类更适合模糊搜索的组件。
  • 【岗位标注】通用 / 运维 / 技术支持

Q9. 数据库 CPU 飙到 100%，你怎么定位？

  • 【考察点】生产应急响应题，考命令链路和”先止血再根治”的思路
  • 【参考回答】止血优先：第一步 top 确认是 mysqld 进程吃 CPU，还是备份（xtrabackup）、监控 agent 之类抢的；第二步 SHOW PROCESSLIST 看有没有一堆长时间 Running 的 SQL，有就是它们——直接 KILL 掉最凶的几条先止血；第三步开慢查询日志或抓 performance_schema 确认是同一类 SQL 还是多类，对命中 SQL 做 EXPLAIN 找索引问题或全表扫描；第四步看资源层面：Buffer Pool 太小导致频繁刷盘、连接数暴涨（连接风暴）、swap 抖动。根治是优化对应 SQL、加索引、或者给大查询分流（只读从库跑分析任务）。我的习惯是平时就把慢查询日志和 processlist 采样接入监控，出事 5 分钟内能定位。
  • 【追问】
    • 追问：怎么确认是不是”连接风暴”？→ SHOW STATUS LIKE 'Threads_connected' 看连接数暴涨曲线，配合应用日志看是不是发版后连接池配置变了或某服务批量重连。
    • 追问：KILL 掉 SQL 会不会有问题？→ 会回滚它所在的事务，正在写数据的话有短暂影响，但比让全库卡死强；KILL 前看一眼是 SELECT 还是长事务 UPDATE，长事务要谨慎，先评估再动手。
  • 【岗位标注】运维 / 技术支持

Q10. 数据量 1000 万行，分页查询 LIMIT 100000, 10 越来越慢，怎么优化？

  • 【考察点】反直觉题：加了索引分页还是慢，考对深分页原理的理解和常用优化手法
  • 【参考回答】深分页慢的本质：LIMIT 100000, 10 要先把前 100010 行都查出来再丢掉前 10 万行，扫描量固定，索引只能加速定位、不能加速”跳过”。三个方案：第一，游标分页（推荐）：WHERE id > 上次返回的最大id ORDER BY id LIMIT 10，靠主键定位，不管翻到第几页都只扫 10 行，但只支持”下一页”不支持跳页；第二，延迟关联：先 SELECT id FROM t ORDER BY id LIMIT 100000, 10 只查主键（能走覆盖索引），再 JOIN 原表取整行，把大扫描留在索引层；第三，跳页是硬需求就物化排序键或接受用缓存。生产上我一般直接推游标分页，配合前端”加载更多”的交互。
  • 【追问】
    • 追问：为什么先查 id 再 join 就快了？→ 第一步只扫索引叶子，10 万行扫描发生在索引里（内存友好、IO 少），最后只回表 10 行；直接 LIMIT 是回表 10 万行。
    • 追问：排序字段不是主键怎么办？→ 游标分页要求排序字段唯一且稳定，可以在排序列上建联合索引让排序走索引，游标条件改成 (id, 排序列) 组合比较。
  • 【岗位标注】通用 / 运维 / DevOps
